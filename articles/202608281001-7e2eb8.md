今週Archicadで検索したら、直接ヒットしたニュースがほぼ無くて、代わりに開発者コミュニティのAIエージェント関連記事ばかり並んでました。正直「Archicadネタが無い週か…」と一瞬手が止まったんですが、よく読むとBIM運用の現場に刺さる話が多くて、むしろ今週はこっちを整理したほうが業務に効きそうだと感じたので、AIエージェントとArchicad運用を絡めてまとめます。うちの社内でもArchicadのテンプレ整備と並行してAI活用の検証が始まっているので、ちょうどタイミングとしてもよかったです。

## 今週のトピック

### AIがコードを書いている間、人は何をするか

[What Do You Do While AI Codes?](https://dev.to/anchildress1/what-do-you-do-while-ai-codes-k8k) は、AIエージェントに処理を任せている5〜20分の空き時間をどう使うか、という現場感のある話でした。「すぐ確認しに行く癖」がボトルネックになる、という指摘が耳に痛い。

これ、Archicadでモデルチェッカーや干渉チェックを回している間の待ち時間にそっくりなんですよね。うちだと大規模物件でIFC書き出しに20分以上かかることもあって、待ちながらつい別の作業に手を出して、結局書き出しエラーの発見が遅れる。AI云々の前に、待ち時間の使い方をチーム内で言語化しておく価値はありそうです。

### AIエージェントが「正しく動いて、間違った先に投稿した」話

[The agent posted successfully. To the wrong account.](https://dev.to/eugeniya_ivanova_4a58eadc/the-agent-posted-successfully-to-the-wrong-account-3kf3) は、AIエージェントがOAuth認証をきちんと通した上で、意図と違うアカウントに投稿してしまった事例。処理は成功、結果は失敗、というやつです。

Archicad × 発注者提出のワークフローに置き換えると笑えない話で、たとえばBIMxやIFCの自動出力を組んだ時に「出力は成功、宛先フォルダが旧版案件」なんて事故は普通に起こりえる。権限とスコープの分離をどう設計するかは、AI以前にBIMマネジメントの課題だと改めて思いました。

### 1000行超のコードをAIとリファクタリングする

[Writing Modern Go with AI](https://dev.to/gde/go-in-practice-writing-modern-go-with-ai-testing-jetbrains-go-modern-guidelines-and-refactoring-151o) は、1,039行のmain.goをガイドライン付きでAIに整理させた記録。ガイドラインを渡すかどうかで出力の質が別物になる、という点が実感的でした。

Archicadのテンプレートや属性マネージャーの整理も似ています。GDLオブジェクトの命名規則、レイヤー構成、分類体系。これらを文書化しないままAIに「整理して」と投げても、たぶん使い物にならない。逆に言えば、社内標準がしっかりしている会社ほどAI活用の伸びしろが大きいはずで、標準化の担当としては追い風だと感じてます。

### ベクトル検索は結局エージェントの記憶層に必要

[Vector Search Is Still the Memory Layer Agents Actually Need](https://dev.to/bengreenberg/vector-search-is-still-the-memory-layer-agents-actually-need-50dn) は、派手さは無いけどエージェントに文脈を持たせるにはベクトル検索が要る、という主張。

Archicadのプロジェクト情報、過去物件のディテール、社内標準図。これらを横断検索する仕組みは、正直まだうちには無いです。設計者が「前の案件の外壁納まりを参照したい」と思っても、結局人力でPLNを開き直している。ここにベクトル検索を噛ませられたら、Archicadの資産価値は跳ね上がると個人的には見ています。

もう一本、[FutureBuilder and StreamBuilder as Anti-Patterns](https://dev.to/gde/futurebuilder-and-streambuilder-as-anti-patterns-why-your-async-boundary-should-be-far-away-from-1d8g) はFlutter寄りの技術論なので今回は割愛します。

## ゼネコンBIM担当としての独自考察


:::message
今週の記事群を通して感じたのは、AIエージェントの議論がそのままArchicad運用の議論と重なってきているということ。ワークフロー自動化、権限設計、社内標準の文書化、過去資産の検索。どれもBIM推進で3年前から言い続けてきたテーマそのものです。

社内標準化への活かし方としては、まずArchicadテンプレートの命名規則と分類体系をMarkdownなりで機械可読な形に落とすことから始めるのが現実的だと思ってます。これは推測ですが、テンプレが文書化されていれば、将来的にAIエージェントに「この物件のテンプレを基準に属性を整えて」と頼めるようになる下地になるはず。

導入ハードルもはっきりしていて、協力会社との連携が最大の壁です。うちの協力事務所はRevit派とArchicad派が混在していて、IFC経由でやり取りしている。ここにAIエージェントを挟むと、認証・スコープ・出力先の管理が一気に複雑化する。冒頭の「正しく動いて間違った先に投稿した」事例を、BIMデータでやらかしたら発注者との信頼問題になる。技術より運用ルールの整備が先、というのが今の実感です。
:::


## まとめ

Archicad単体のニュースは薄い週でしたが、周辺のAI議論をArchicad運用に翻訳すると、やることは意外とはっきりしてました。テンプレの文書化、待ち時間のルール化、権限設計の見直し。派手さは無いけど、来週の社内定例で提案するネタとしては十分すぎるくらい。まずはテンプレのMarkdown化から手を動かします。
